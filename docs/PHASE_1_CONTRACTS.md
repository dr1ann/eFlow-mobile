## Generated lifecycle RPC signatures

| Workflow | Function and generated arguments | Mobile rule |
| --- | --- | --- |
| Start, resume, or other task state change | `transition_task_status(p_task_id, p_to_status, p_feedback?, p_reason?)` | Use the RPC; never write `tasks.status` directly. |
| Save subtask progress | `save_subtask_progress(p_subtask_id, p_percent_complete, p_blocker_category?, p_blocker?, p_next_step?, p_note?, p_attachment_path?, p_attachment_name?)` | Online only; the server rejects 100% progress and locked states. |
| Submit subtask evidence | `submit_subtask_for_review(p_subtask_id, p_submission)` | The payload is JSON and needs a non-empty `note` plus evidence metadata. |
| Decide a subtask review | `decide_subtask_review(p_subtask_id, p_approve, p_feedback?)` | The server prevents self-review and requires feedback when changes are requested. |
| Submit parent task | `submit_task_for_review(p_task_id, p_submission)` | Online only; all subtasks must already be approved. |
| Decide parent review | `decide_task_review(p_task_id, p_approve, p_feedback?, p_audit_hash?)` | The server remains the reviewer-routing and self-review authority. |

The deployed generated types confirm the function names and arguments, not the policy results. `transition_task_status` currently generates an array return; the other lifecycle functions generate a single task or subtask return.

## Upstream behavior cross-check

The inspected upstream migration defines the following behavior, which mobile mirrors only as client guidance until it is proven against the selected non-production project:

- Subtask states are `todo`, `in_progress`, `for_review`, `changes_requested`, and `completed`. The server disallows direct contributor completion.
- Progress only permits `0..99`; evidence-backed review submission sets a subtask to 100% and `for_review`.
- A submission needs at least one evidence record and a non-empty note.
- A subtask reviewer cannot decide their own submission; an administrator exception is server-side.
- A task cannot enter `for_review` while any child `is_completed` is false. Mobile also requires each child to show `completed` and `isCompleted` before enabling the parent submit control.
- Only the effective Task Lead may create, assign, reorder, reschedule, delete, or change execution rules for subtasks. Contributors may still save progress and submit evidence for their assigned subtasks.
- The upstream migration adds the three subtask progress/submission tables to Realtime. The selected project's publication still needs a live event probe.

## Deliberately unverified and blocked

| Area | Required evidence before enabling the mobile feature |
| --- | --- |
| RLS reads and RPCs | Allowed and denied calls for assigned contributor, Task Lead, primary reviewer, backup reviewer, unrelated employee, self-review collision, and inactive/missing profile. |
| Evidence Storage | Bucket name, exact object-path convention, MIME allowlist, byte/count limits, upload/delete policies, signed URL lifetime, and orphan-cleanup owner. The inspected `fresh_schema.sql` has a broad authenticated `taskfiles_rw` policy for task buckets, and none of the 61 supplied migrations replaces it with task-scoped object access. Mobile must not rely on or reproduce that policy. The app therefore normalizes and locally previews selected asset metadata only; it does not upload, persist the local URI, or present a selection as submitted evidence. |
| Notifications and announcements | Recipient-only reads/updates, announcement visibility rules, and safe Realtime delivery. |
| Task discussion | Participant-only `task_comments` read/insert policy. Attachments, editing, and general chat are not Phase 1 scope. |
| Project overview | Read-only RLS result for a task-linked project, including denied and deleted records. |
| Device acceptance | Android and iOS Expo Go checks for session lifecycle, picker URI behavior, accessibility, safe areas, keyboard, and foreground reconnect. |

No client-side role condition is treated as authorization. UI eligibility only avoids obviously invalid actions; RLS and the RPCs decide every sensitive read and mutation.
